# Ожирун (ojirun) — Telegram-бот дневника питания

## Назначение

Ожирун (`ojirun`) — публичный Telegram-бот, дневник питания. Работает в личных сообщениях и в любых группах, куда его добавят; пользоваться им могут только подписчики канала автора (`TELEGRAM_REQUIRED_CHANNEL`).

Бот принимает от зарегистрированных пользователей текстовое описание еды и/или фото, анализирует прием пищи через OpenRouter, считает КБЖУ, показывает результат в том же чате, сохраняет подтвержденные записи в PostgreSQL и каждое утро присылает в ЛС отчет за предыдущий день тем, у кого были записи.

Интерфейс бота: русский язык. Go-модуль: `ojirun`.

## Технологический стек

- Язык: Go 1.26.
- База данных: PostgreSQL 17, драйвер pgx v5.
- Telegram: собственный минимальный HTTP-клиент Bot API (`infrastructure/telegram`) — нужны Rich Messages, эфемерные сообщения и стили кнопок, которых нет в готовых библиотеках.
- Запуск локально и на сервере: Docker Compose.
- AI-провайдер: OpenRouter.
- Модели: `OPENROUTER_MODEL` — список vision-моделей через запятую; первая — основная, остальные — backoff. Если API конкретной модели не отвечает (transport-ошибка, HTTP-ошибка, error-ответ провайдера, пустые choices), клиент переключается на следующую модель списка. Ошибка декодирования structured-ответа (модель ответила, но контент не по схеме) ретраится на той же модели.
- Конфигурация: `.env`.
- Промпты: отдельные файлы в `prompts/`.
- Локальное хранилище фото: файловая система или volume Docker; метаданные фото обязательно пишутся в БД.
- Линтер: golangci-lint v2 (`.golangci.yml`), CI — GitHub Actions.

Перед выбором библиотек, API-параметров и форматов сообщений нужно проверять актуальную документацию через Context7 или официальные документы Telegram/OpenRouter.

## Правила кода

- Комментарии в коде не пишутся: ни doc-комментарии, ни inline, ни `--` в SQL-миграциях. Пояснения — в этом файле, README или описании изменений. Исключение — директивы вроде `//go:embed`.
- `golangci-lint run ./...`, `go vet ./...`, `go test -race ./...` и `go mod tidy -diff` должны проходить: то же проверяет CI.
- Новая схема БД — только новой миграцией в `migrations/` с очередным номером; примененные миграции не меняются по смыслу (раннер отмечает их по имени файла).

## Telegram-ограничения и требования

- Бот публичный: работает в ЛС и в любой группе, куда его добавили; привязки к конкретной группе нет. Для работы в группах у бота отключен privacy mode.
- Бот не удаляет исходные сообщения пользователей в сценарии добавления еды.
- Пользоваться ботом могут только подписчики канала `TELEGRAM_REQUIRED_CHANNEL`. Подписка проверяется через `getChatMember` (бот должен быть администратором канала, это проверяется при старте); подтвержденная подписка кешируется на 10 минут, отказ не кешируется. Если Telegram API не ответил, проверка считается проваленной как системная ошибка: бот не пускает пользователя и просит попробовать позже (`render.SubscriptionCheckFailed`), а задача отчета уходит на повтор, а не в `skipped_unsubscribed`. Без подписки бот отвечает ссылкой на канал и кнопкой «Я подписался» (в группе — эфемерно), на callback-кнопку — alert. В группах проверка запускается только для действий, адресованных боту (команды, фото, ожидаемый текст), а не для обычной переписки.
- Регистрация проходит в личных сообщениях с ботом. `/start`, `/profile`, `/settings` в группе отвечают эфемерным сообщением «Напишите мне в ЛС».
- Обработка еды запускается командой `/add` или фото-сообщением — в ЛС или в группе. В группе фото от незарегистрированных пользователей молча игнорируется, как и команды, адресованные другим ботам (`/add@other_bot`).
- Бот не реагирует на обычные текстовые сообщения без команды, кроме режима ввода `/add`, активной регистрации или настроек в ЛС и ожидаемой текстовой корректировки. В ЛС на прочий текст бот отвечает: незарегистрированному — предложением пройти `/start`, зарегистрированному — списком команд с меню.
- Если пользователь отправляет фото еды без команды, бот обрабатывает его как добавление еды; подпись к фото используется как описание.
- Все callback-кнопки закрываются одним ответом на callback query (`callbackAnswer` в `presentation/telegram/callback.go`).
- Все действия имеют видимый статус: бот редактирует свое предыдущее сообщение или отправляет новое.
- В группах бот пишет публично только итог принятой еды и карточку `/stats` (по кому угодно). Все остальное — статусы, «в очереди», карточка с кнопками `Принять`/`Редактировать`/`Удалить`, приглашение `/add`, подсказки и отказы, уведомления о подписке и о лимите — отправляется эфемерными сообщениями (Bot API 10.3: `ephemeral_message_parameters.receiver_user_id`), которые видит только адресат; правка и удаление — `editEphemeralMessageText`/`deleteEphemeralMessage`. Решение принимает `presentation/telegram/delivery.go`: группа определяется по отрицательному `chat_id`. Доставка эфемерного сообщения офлайн-пользователю не гарантирована. Эфемерные сообщения отправляются без `reply_parameters` (`withEphemeral` их сбрасывает): Telegram показывает цитату в эфемерном ответе как «Deleted message», а на эфемерное сообщение пользователя можно ответить только эфемерно и в первые секунды. Reply остается только у публичных сообщений — итога принятой еды и карточки `/stats`. В ЛС — обычные сообщения.
- Для отчетов и карточек КБЖУ используются Rich Messages (Bot API 10.1+): `sendRichMessage` с `rich_message` из Markdown-контента, обновление — `editMessageText` / `editEphemeralMessageText` с `rich_message`.
- Таблицы рендерятся Rich Markdown pipe-table синтаксисом с учетом ограничений Telegram: до 20 колонок, в ячейках только inline-форматирование.
- Если Rich Message не отправился, renderer падает обратно на обычный `sendMessage`. Fallback не должен быть основным путем.
- Рендер изолирован в `presentation/telegram/render`, чтобы формат сообщений менялся без переписывания бизнес-логики.

## Основные команды

### `/start`

Единая команда входа и регистрации (отдельной команды `/register` нет).

Работает в личных сообщениях. `/start` (а также deep link `t.me/<bot>?start=register`) запускает или перезапускает регистрацию: бот публикует одну интерактивную карточку и редактирует ее на месте по мере ответов.

- карточка показывает чек-лист полей и текущий вопрос;
- ответы-кнопки (пол, активность, цель) и текстовые ответы (возраст, рост, вес) обновляют ту же карточку через `editMessageText`;
- текстовые ответы пользователя бот удаляет, чтобы в чате оставалась одна карточка; сообщение `/start` остается;
- если редактирование не удалось, бот удаляет устаревшую карточку и присылает новую (id карточки хранится в `registration_sessions.bot_message_id`);
- в конце бот показывает итоговую карточку с данными и нормой и отдельным сообщением включает меню.

Собираемые данные: пол, возраст, рост, вес, уровень активности, цель (похудение / поддержание / набор). Имя для отчетов берется из Telegram-профиля.

Норма калорий и макронутриентов: формула Mifflin-St Jeor, коэффициент активности, корректировка калорий по цели (похудение — дефицит, поддержание — без изменений, набор — профицит). Коэффициенты живут в `domain/nutrition.go`, а не в handler-коде.

### Меню в ЛС

В личном чате у бота постоянная reply-клавиатура (`ReplyKeyboardMarkup`, `is_persistent`): «🍽 Добавить еду» (зеленая, `style: success`) → `/add`, «📊 Статистика» → `/stats`, «👤 Профиль» → `/profile`, «⚙️ Настройки» → `/settings`, «💡 Как это работает?» → `/help`. Нажатие приходит текстом кнопки и маппится на команду (`presentation/telegram/menu.go`). Клавиатура прикрепляется к справке, статистике в ЛС и к сообщению после регистрации; у профиля вместо нее inline-кнопки (у сообщения может быть только одна `reply_markup`), а постоянная клавиатура остается от прежних сообщений. В группах reply-клавиатура не используется: она показалась бы всем.

### `/help`

Справка «Как это работает»: в ЛС с меню, в группе эфемерно.

### `/profile`

Работает в личных сообщениях. Показывает данные пользователя и норму; если норма задана вручную, помечает это. Под сообщением inline-кнопки: «⚙️ Изменить данные» (`profile:settings`) открывает `/settings`, «♻️ Пересчитать заново» (`profile:restart`) запускает регистрацию, как `/start`.

### `/settings`

Работает в личных сообщениях.

Ручная правка профиля без повторной регистрации — например, когда норму КБЖУ назначил тренер. Сначала карточка-меню с текущими значениями и выбором, что изменить: отдельное поле (пол, вес, калории, белки, жиры, углеводы), «🎯 Вся норма КБЖУ» (калории → белки → жиры → углеводы), зеленая «Настроить всё» (все шесть полей) или красная «Отмена». Текст в режиме меню не принимается — карточка просит выбрать кнопкой. Затем та же карточка проходит только выбранные поля по порядку. На каждом шаге:

- новое значение отправляется сообщением (пол — кнопками), сообщение удаляется;
- зеленая кнопка `Оставить текущее: <значение>` пропускает поле;
- красная кнопка `Отмена` закрывает редактор без сохранения.

Профиль сохраняется только после последнего выбранного поля; итоговая карточка показывает выбранные поля и отмечает измененные пометкой `было …`. Шаг сессии — `menu` или ключ поля, выбранные поля — `fields` в `payload_json` (пусто — все поля, так продолжают работать сессии, начатые до появления меню). Если изменена хотя бы одна цель КБЖУ, `formula_version` становится `manual`; `/start` возвращает расчет по формуле. Пределы значений — в `domain/settings.go`. Сессия — `registration_sessions` с `kind = settings`.

### `/stats`

Работает в ЛС и в группе. Показывает статистику за сегодня (подтвержденные записи за текущий день в `APP_TIMEZONE`): количество приемов пищи и прогресс по калориям, белкам, жирам и углеводам отдельными прогресс-барами `съедено / норма` с процентом.

- Без аргумента — статистика отправителя.
- В группе `/stats @username` показывает статистику участника (поиск по `telegram_username` без учета регистра). Виден только тот, кто сам вел дневник в этой группе, иначе — «не нашёл»: публичный бот не раскрывает чужую статистику. В ЛС аргумент игнорируется.
- Карточка отправляется reply на команду и в группе публична; ошибки — эфемерно.

Цвет прогресс-бара показывает близость к норме, а не заполненность: попасть в норму — хорошо, недобор и перебор — одинаково плохо. 🟩 — в пределах ±10% от нормы, 🟧 — в пределах ±25%, 🟥 — дальше. Тот же бар используется в карточке КБЖУ.

### `/add`

Работает в группе и в ЛС.

`/add` без содержимого включает режим ввода: бот отвечает просьбой описать еду и красной кнопкой `Отменить`. Следующее сообщение автора в этом чате — текст или фото (подпись — описание) — анализируется как прием пищи, а приглашение бот удаляет. Режим ввода хранится в `registration_sessions` (`kind = meal_input`) и живет 30 минут; повторный `/add` заменяет его, отменить может только автор. Во время режима ввода обычный текст автора считается едой, а не корректировкой.

Если текст или фото пришли прямо в команде, режим ввода не нужен:

```text
/add гречка с курицей и салат
```

Также можно отправить фото без команды; подпись к фото — описание еды.

- Незарегистрированному пользователю бот предлагает пройти регистрацию в ЛС.
- Без подписки на канал запись не создается — бот просит подписаться.
- Если пользователь указал точные значения КБЖУ вручную, промпт сохраняет явно указанные числа и не заменяет их оценкой модели без причины.

Антифрод: один пользователь может добавить не больше `MAX_MEALS_PER_DAY` (по умолчанию 10) записей за календарные сутки в `APP_TIMEZONE` — суммарно в ЛС и во всех группах. Считаются все созданные записи, включая удаленные и нераспознанные: каждая стоила AI-запрос; корректировки не считаются, но их не больше `domain.MaxCorrectionsPerEntry` (5) на запись. Подсчет и вставка идут в одной транзакции под `pg_advisory_xact_lock` по пользователю (`meal.Repository.CreateEntryWithinLimit`), поэтому одновременные сообщения не обходят лимит. При исчерпании бот отвечает (в группе — эфемерно) и не открывает режим ввода `/add`.

### `/readd`

Работает в группе и в ЛС, ответом автора на свое исходное сообщение с едой. Повторяет распознавание, например если фото не скачалось или разбор не понравился. Чужое сообщение — отказ «только автор»: иначе любой участник группы мог бы тратить чужой лимит и AI-запросы.

У сообщения может быть только одна живая запись. Если запись уже есть (`FindByMessage` по `chat_id` и `source_message_id`), `/readd` заменяет ее: прежняя переводится в `deleted` (принятая — с audit-событием), ее карточки удаляются (`MealMessenger.Deleted` убирает и эфемерную карточку, и публичную), затем создается новая. Запись, которая еще обрабатывается (`received`, `downloading_photo`, `analyzing`, `reanalyzing` — `Status.InFlight`), заменить нельзя: бот просит дождаться результата. Новая запись проходит те же проверки, что и обычная: регистрация, подписка, лимит, причем лимит проверяется до удаления прежней записи.

### `/yesterday`

Работает в группе и в ЛС, только ответом (reply) на сообщение. Переносит уже добавленную запись на предыдущий календарный день — для еды, добавленной задним числом.

Ответить можно на исходное сообщение с едой или на публичную карточку бота: запись ищется по `chat_id` и `source_message_id` либо `bot_message_id`.

- переносить дату может только автор записи;
- переносится только запись в статусе `pending_confirmation` или `accepted`;
- новая дата — календарный день создания записи (`created_at` в `APP_TIMEZONE`) минус сутки, а не текущий `meal_date`, поэтому повторный вызов идемпотентен.

Перенос меняет только `meal_date`, и запись сразу уходит из статистики за сегодня во вчерашнюю.

## Сценарий добавления еды

1. Пользователь отправляет `/add` и затем описание или фото (режим ввода), `/add` с текстом и/или фото либо просто фото еды — в ЛС или в группе.
2. Бот проверяет регистрацию, подписку и дневной лимит и создает запись со статусом `received`.
3. Бот сразу показывает статус: «Принял запись» или «в очереди — перед вами N», если воркеры заняты. В группе это эфемерное сообщение-ответ на еду, которое потом правится по этапам и превращается в карточку; его видит только автор. В ЛС сообщений о статусе нет вовсе — вместо них «thinking»-черновик (`sendRichMessageDraft`, `draft_id` = id сообщения с едой), который сменяется по этапам и исчезает, когда бот присылает итог.
4. Бот ставит задачу анализа в очередь `meal`; исходное сообщение пользователя остается в чате.
5. Воркер скачивает фото из Telegram и сохраняет его локально. Из вариантов размера выбирается самый крупный не больше 1280 px по большей стороне (`Message.BestPhoto`).
6. Воркер отправляет в OpenRouter системный промпт, текст пользователя, фото и JSON Schema structured output.
7. Structured output валидируется и нормализуется.
8. Результат сохраняется ревизией, запись переходит в `pending_confirmation`. В `ai_request_json` ревизии запрос хранится без байтов фото: вместо data URL — ссылка `photo:sha256:<hex>`, совпадающая с `photos.sha256` (иначе база росла бы на копию каждого фото в base64).
9. Карточка в Rich Message: что распознано, таблица КБЖУ, прогресс калорий за день и кнопки `Принять`, `Редактировать`, `Удалить`. Фото не вставляется в Rich Message и не переотправляется ботом. В группе карточка — правка эфемерного статуса. В ЛС по Bot API черновик закрывается только новым отправленным сообщением, поэтому карточка (как и «не удалось» и «не распознал») приходит одним новым сообщением-ответом на еду (`MealMessenger.finalize`); при корректировке прежняя карточка удаляется и приходит новая. Черновик живет 30 секунд: если запись долго ждет в очереди, он может исчезнуть до начала анализа, а затем появится снова с первым этапом.
10. До нажатия `Принять` запись не учитывается в дневной статистике.

## Кнопки результата

### `Принять`

- Доступна только автору записи.
- Переводит запись в `accepted`.
- В ЛС убирает кнопки; в группе публикует для всех итоговую карточку без кнопок (reply на сообщение с едой) и удаляет эфемерную карточку автора. Повторное нажатие ничего не публикует.

### `Редактировать`

- Доступна только автору записи.
- Переводит запись в `awaiting_correction`, карточка просит прислать корректировку и показывает кнопку `Отменить`.
- Корректировка — обычный текст автора в том же чате, где создана запись.
- Повторный запрос в OpenRouter ставится в очередь `meal` и включает исходный текст, предыдущий structured output, текст корректировки, исходное фото и отдельный correction-промпт.
- Новый результат сохраняется новой ревизией, старая остается в истории.
- Не больше `domain.MaxCorrectionsPerEntry` (5) корректировок на запись (`MealRevision.CanCorrect`): при исчерпании кнопка отвечает alert-ом, а текст, присланный в режиме ожидания, возвращает карточку с кнопками без пересчета.

### `Удалить`

- Доступна только автору записи.
- Переводит запись в `deleted`, карточка бота удаляется или редактируется в «Удалено».
- Удаление уже принятой записи создает audit-событие, а не стирает запись физически.

## Дневной отчет

Каждый день в `DAILY_REPORT_TIME` (по умолчанию 09:00, `Europe/Moscow`) бот отправляет отчеты за предыдущий календарный день.

Отчет уходит только в ЛС и только активным пользователям — у кого за этот день есть хотя бы одна подтвержденная запись в любом чате. Нет записей — нет отчета и нет запроса к OpenRouter. Отписавшимся от канала отчет не отправляется. В группы отчеты не публикуются.

В отчете:

- Rich Markdown таблица подтвержденных приемов пищи: время, блюдо, ккал, белки, жиры, углеводы;
- строка «Итого» и сравнение с нормой;
- блок рекомендаций от OpenRouter.

Планирование: один SQL-запрос ставит в очередь `report` задачу на каждого активного пользователя (дедупликация по `daily_report:<user>:<date>`), `REPORT_WORKERS` воркеров собирают и отправляют отчеты в своем темпе. Если бот был выключен в момент рассылки, при старте отчеты за вчера ставятся в очередь повторно. Повторный запуск не дублирует отчет: слот `daily_reports` уникален по пользователю, чату и дате.

## Статусы записи

- `received` — запись создана;
- `downloading_photo` — фото скачивается;
- `analyzing` — идет запрос к OpenRouter;
- `pending_confirmation` — результат показан пользователю;
- `awaiting_correction` — ожидается корректировка;
- `reanalyzing` — идет повторный анализ;
- `accepted` — пользователь принял запись;
- `deleted` — пользователь удалил запись;
- `failed` — обработка завершилась ошибкой.

Статусы хранятся в БД, чтобы бот корректно восстанавливался после перезапуска.

## Параллельность и надежность

- Все handler-операции принимают `context.Context`; updates обрабатываются пулом (`MAX_CONCURRENT_UPDATES`).
- Записи и callback-действия используют транзакции PostgreSQL; изменения статуса атомарны, callback-действия проверяют автора и идемпотентны.
- Ошибки Telegram, OpenRouter и БД логируются структурированно (slog JSON).

Очередь задач (`jobs`, `service.JobWorkers`):

- медленная работа — AI-анализ еды, корректировки, ежедневные отчеты — выполняется не в обработчике update, а воркерами durable-очереди в PostgreSQL;
- задача забирается через `FOR UPDATE SKIP LOCKED` с арендой на 5 минут: несколько инстансов делят нагрузку, после падения воркера задача снова доступна;
- отдельные очереди и пулы: `meal` (`MAX_CONCURRENT_AI` воркеров) и `report` (`REPORT_WORKERS`), чтобы рассылка отчетов не задерживала анализ еды;
- успешная задача удаляется; ошибка — повтор с backoff до `max_attempts`; ответ Telegram 429 — повтор через `retry_after`; 400/403 (например, пользователь заблокировал бота) — сразу `failed`;
- обработчики идемпотентны: задача анализа, чья запись уже вышла из `received`/`downloading_photo`/`analyzing`, ничего не делает; повторную отправку отчета исключает слот `daily_reports`;
- при остановке бот дожидается задач в работе.

## Безопасность

- Секреты только в `.env`, без коммита в репозиторий.
- Не логировать токены, полные payload с приватными данными и сырые фото.
- Проверять размер скачиваемых файлов и ограничивать типы поддерживаемыми изображениями.
- Экранировать пользовательский текст перед вставкой в Rich Markdown, HTML или fallback.
- Проверять права пользователя на каждое действие с записью.
- При старте проверять, что бот — администратор канала `TELEGRAM_REQUIRED_CHANNEL`.
- Использовать least privilege для пользователя PostgreSQL.

## Архитектура Go-приложения

Код выстроен по DDD / Clean Architecture без догматизма: один bounded context `internal/context`, разделенный на слои. **Зависимости направлены внутрь:** `presentation` → `application` → `domain`; `infrastructure` реализует интерфейсы, объявленные внутренними слоями; `domain` не импортирует остальные слои. `internal/bootstrap` — composition root, единственное место, знающее обо всех слоях.

```text
cmd/bot/main.go                    entrypoint: сигналы, bootstrap.New().Run()/Stop()
cmd/migrate/main.go                отдельный прогон миграций
internal/bootstrap/
  config.go                        Config из env, ParseClock, LoadDotEnv
  prompts.go                       загрузка prompts/*.md
  logger.go                        slog JSON logger
  registry.go                      сборка зависимостей: repos → services → usecases → presentation
  app.go                           long-poll, пул updates, воркеры очередей, планировщик отчетов, graceful shutdown
internal/context/
  domain/                          сущности и value objects, без зависимостей
    errors.go                      sentinel-ошибки (ErrUserNotFound, ErrDailyMealLimit, …)
    user.go profile.go nutrition.go settings.go
    meal.go revision.go analysis.go photo.go session.go report.go job.go ai.go
  application/
    service/                       оркестрация поверх портов
      analyzer.go                  порт Analyzer
      subscription.go              проверка подписки на канал с кешем
      registration.go settings.go meal_input.go
      meal.go                      MealPipeline: фото → AI → ревизия, порт MealNotifier
      jobs.go meal_jobs.go         JobWorkers (пул воркеров очереди), MealJobs (задачи анализа)
      report.go                    планирование и отправка отчетов
      session.go                   порт sessionStore
    usecase/                       add_meal (лимит), meal_actions, get_profile, get_stats
  infrastructure/
    telegram/                      HTTP-клиент Bot API, типы, markup, callbacks, APIError, эфемерные методы
    openrouter/                    structured-output клиент с failover моделей
    files/                         локальное хранилище фото + Archiver
    httpx/                         HTTP-клиент с прокси
    db/postgres/                   пул и миграции + репозитории: user/ profile/ session/ meal/ photo/ report/ job/
  presentation/telegram/           доставка: роутинг апдейтов → usecase/service, рендер
    api.go                         порт API: нужные методы Telegram-клиента
    router.go                      разбор апдейтов и маршрутизация
    meal.go meal_input.go correction.go callback.go registration.go settings.go stats.go report.go
    subscription.go                требование подписки
    delivery.go ephemeral.go       ответы адресату: эфемерные в группах, обычные в ЛС
    messages.go                    MealMessenger: реализация MealNotifier
    menu.go card.go                меню ЛС, редактирование интерактивных карточек

prompts/
migrations/
.github/workflows/ci.yml           CI
.golangci.yml                      линтер
```

Принципы:

- **Порты объявляет потребитель.** Каждый usecase/service объявляет узкие интерфейсы; infrastructure и presentation их реализуют. Telegram и OpenRouter не протекают внутрь как конкретные типы.
- **Доменные сущности** имеют конструкторы (`NewProfile`, `NewRevision`) и поведение (`Status` + `CanTransition`, `NutritionAnalysis.Normalize/HasFood`, `Profile.ApplySettings`). ID генерирует БД (`gen_random_uuid`).
- **Репозитории** — по агрегату: `query.go` (SQL-константы) + `repository.go` (методы, перевод ошибок драйвера в доменные sentinel-ошибки). Транзакции живут внутри своего агрегата.
- **Пайплайн еды** разнесен через порт `MealNotifier`: `service.MealPipeline` ведет оркестрацию, `presentation` рендерит статусы и карточки, долгая работа идет через очередь `meal`.
- **Рендер** изолирован в `presentation/telegram/render`.
- Тестами покрыты расчеты, нормализация AI-ответа, рендер, переходы статусов, сценарии роутера, очередь, отчеты, подписка и лимит.

## Docker Compose

- `compose.yml` — полный стек: бот (`bot`), PostgreSQL, volume `postgres_data` и volume фото `photo_storage`. Бот ждет healthcheck Postgres и применяет миграции на старте.
- `compose.local.yml` — только PostgreSQL для локального запуска `go run ./cmd/bot`.

Порт PostgreSQL в обоих файлах проброшен только на `127.0.0.1:5432`: бот ходит в базу по docker-сети, а снаружи хоста база не видна.

Миграции идемпотентны и выполняются на старте; отдельный прогон — `cmd/migrate`. Образ собирается из `Dockerfile`, бинарник — `/app/ojirun`.

## Бэкапы

`scripts/backup.sh` снимает `pg_dump -Fc` базы через `docker compose exec postgres` и `tar.gz` тома фото в `BACKUP_DIR` (по умолчанию `/srv/main/backups/ojirunbot`), оставляя `BACKUP_KEEP` (по умолчанию 5) последних копий каждого вида. `PROJECT_DIR` переопределяет каталог проекта (по умолчанию — родитель `scripts/`), `PHOTO_VOLUME` — имя тома (по умолчанию `<каталог проекта>_photo_storage`). На сервере скрипт запускает cron раз в сутки. Восстановление: `pg_restore -U nutrition -d nutrition --clean --if-exists` внутри контейнера Postgres и распаковка архива в том `photo_storage`.

## Критерии готовности

- Пользователь регистрируется в ЛС и получает норму КБЖУ.
- Бот пускает только подписчиков канала `TELEGRAM_REQUIRED_CHANNEL`.
- Пользователь добавляет еду текстом и/или фото в группе или в ЛС в пределах дневного лимита.
- Бот оставляет исходное сообщение, показывает статус и результат с КБЖУ и кнопками; в группе промежуточные сообщения эфемерные.
- Бот получает structured output от OpenRouter и валидирует его.
- Только автор может принять, редактировать или удалить свою запись; принятая запись публикуется в группе.
- Принятые записи сохраняются в PostgreSQL, фото сохраняются локально и связаны с записью.
- Утром бот отправляет в ЛС отчет за вчера каждому, у кого были подтвержденные записи; повторный запуск не дублирует отчеты.
- CI проходит: линтер, тесты, миграции, сборка образа.
